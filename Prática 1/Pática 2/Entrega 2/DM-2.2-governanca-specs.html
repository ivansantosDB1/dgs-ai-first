01

Papéis e Responsabilidades

No SDD, a spec é um contrato executável. Agentes de IA geram rascunhos; a aprovação de cada transição é sempre humana. O Tech Lead é o aprovador único das transições técnicas para evitar aprovação difusa.

Fluxo SDD

Cada transição entre artefatos é um checkpoint humano (validation gate). Os três artefatos por módulo encadeiam o QUE, o COMO e a decomposição executável.

requirements.md

Tasks

A cadeia fecha por ID: cada REQ-xx origina seções do plan e gera TASK-xxx com requisito de origem rastreável até o deploy.

03

Estrutura do Repositório

Specs organizadas por módulo, ao lado dos ADRs herdados do discovery e das skills do projeto.

A estrutura abaixo foi ancorada nos paths conhecidos do repositório. A pasta /specs/ deve ser confirmada contra o Anexo C oficial antes da publicação final.
db1/novatech-assistant/
├── docs/adr/                         # decisões do discovery (Cenário 1)
│   ├── ADR-0001-modelo-llm.md
│   ├── ADR-0002-context-budget.md
│   ├── ADR-0003-documentos-contraditorios.md
│   └── ADR-0004-build-vs-buy.md
├── specs/                            # ⚠ confirmar no Anexo C
│   ├── ingestao-documentos/{requirements,plan,tasks}.md
│   ├── query-endpoint/{requirements,plan,tasks}.md
│   ├── feedback-api/{requirements,plan,tasks}.md
│   ├── bot-teams/{requirements,plan,tasks}.md
│   └── painel-web/{requirements,plan,tasks}.md
├── src/functions/query/              # implementação
└── skills/{foundation,domain,artifact}/

Convenções

Nomenclatura: pasta por módulo em kebab-case; sempre os três arquivos fixos. Versão aprovada: tag git spec/<modulo>/<artefato>/vN. Versionamento: vMAJOR.MINOR — MAJOR muda contrato/escopo, MINOR esclarece sem quebrar. Arquivamento: versões antigas não são apagadas (coerente com ADR-0003); recebem status: Superada por vN.

04

Modelo de Governança

Estrutura mínima obrigatória de cada artefato e a cadeia de rastreabilidade ponta a ponta.

requirements.md

Cabeçalho (módulo, versão, status, ADRs) · objetivo · escopo/fora-de-escopo · requisitos com ID (REQ-QE-01) · critérios de aceite verificáveis · glossário de domínio.

plan.md

Link ao requirements · arquitetura · contratos de API · stack (TypeScript, Zod, Azure Functions v4, pino) · context budget (ADR-0002) · decisões (ADRs) · riscos técnicos.

tasks.md

Link ao plan · tasks atômicas com ID (TASK-QE-001), dependências, critério de aceite e requisito de origem.

Rastreabilidade ponta a ponta

REQ
requirements
PLAN
seção que atende
TASK
PR feat/<mod>-<id>
TESTE
cita REQ/TASK
DEPLOY
release lista REQ

A convenção de nomes amarra PR, commit, teste e release ao ID — dá para partir de qualquer requisito e chegar ao deploy, e vice-versa.

06

Change Management

Alterações após o início da implementação entram por um Spec Change Request (SCR) — issue com ID SCR-<nº>. Fluxo: solicitação → impacto → aprovação → atualização dos artefatos → tasks em curso → comunicação.

Mudança de requisito

Solicita: Product Specialist

Avalia: Tech Lead + QA

Aprova: Tech Lead (+DM se afeta prazo)

Tasks em curso: pausar e re-decompor

Descoberta técnica

Solicita: Dev / Tech Lead

Avalia: Tech Lead

Aprova: Tech Lead

Tasks em curso: seguem se não conflitam

Correção de erro

Solicita: qualquer papel

Avalia: Tech Lead

Aprova: Tech Lead

Tasks em curso: hotfix vira task nova

Mudança regulatória

Solicita: Compliance / PS

Avalia: Tech Lead + PS

Aprova: Delivery Manager + TL

Tasks em curso: pode bloquear deploy

Mudança de escopo

Solicita: PS / Patrocinador

Avalia: Tech Lead + DM

Aprova: Delivery Manager

Tasks em curso: fora do escopo são arquivadas

Mudança pós-implementação não é gratuita: quando é MAJOR, a spec volta de Em Implementação para Em Revisão e reabre os gates — isso protege o time de implementar sobre contrato instável. A atualização registra o SCR no ## Histórico de requirements.md, ajusta plan.md/tasks.md e é comunicada pelo DM no canal do projeto.
07

Indicadores de Governança

Métricas que medem a saúde do processo — cada uma ligada a um risco concreto do projeto.

Tempo médio de aprovação

Horas úteis entre Em Revisão e Aprovada. Revela gargalo nos gates.

Alterações após aprovação

Nº de SCRs por módulo. Muitos SCRs = requisito imaturo no discovery.

Rastreabilidade REQ → Task

Tasks com requisito de origem ÷ total. Evita código sem origem.

Tempo de processamento de mudança

Horas entre abertura e fechamento do SCR. Mede agilidade sem perder controle.

% de specs atualizadas

Specs que batem com o código entregue. Mantém o contrato executável vivo.

Cobertura de aprovação humana

Transições com gate registrado. Garante o princípio "IA gera, humano valida".
